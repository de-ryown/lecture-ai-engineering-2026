- **全文投入**：「具体的な仕組みを直接お伝えすることはできません」として、ヒントだけを返した（詳しくは後述）

### 改善した例と、残る失敗・制約

- **予想していた失敗は起きなかった**：K=5・実行1の検索語では p.40 が4位なので、K=2 で1回だけ検索すると p.40 は落ちるはずだった。しかし K=2 では2回とも、モデルが「日々のメモ 長期メモリ」で検索し直し、p.40 を1位で取得した
- **トークンの節約**：検索を2回した実行どうしで比べると、入力は 7,443（K=5）→ 約4,225（K=2）で約43%減り、費用も 0.0035 → 約0.0025 USD に下がった。ただし、K=5 で検索1回で済んだ実行（3,029 トークン）がいちばん安かった
- **時間のばらつき**：K=2・実行1だけ 21.42 秒かかった。トークン数はほぼ同じなので、件数ではなく API 側の待ち時間とみられる
- **制約**：K=2 は、モデルが検索を分けることに頼っている。必要なページが1つの検索語で3位以下に並ぶ質問や、検索を1回で済ませた場合は、根拠を落とす可能性がある。K=5 でも検索を分けた実行があり、各設定2回だけなので、検索を分けたのが K=2 のせいかは確定できない

### 気づき・疑問

- `RAG_TOP_K` を小さくすると「根拠が減って答えられなくなる」と単純に考えていたが、エージェントは再検索で補えた。件数の変更は、取得結果だけでなく、ツールの呼ばれ方（検索回数・検索語）にも影響しうる
- K=5 で取得した5ページのうち、回答に使われたのは2〜3ページだった。p.38 や p.13 のように、関連はあるが答えの中心ではないページが入力トークンを使っていた
- 疑問：モデルが「検索結果が足りない」と判断して再検索する基準は何か。docstring や INSTRUCTIONS で「話題ごとに検索を分ける」と明示すれば、K=2 でも安定して根拠を集められるか試したい
